# Goal
Make the portal pre-warm wait for the landing cell's model loads to be issued and finished, not only for the cell to commit. Then a nonzero `--max-asset-loads-in-flight` (impl-1060) cannot end the prestream wait early and push the load burst back onto the crossing. Also fix two small findings from review-1079. Track: Phase 2.

Queued and in-flight loads count as pending in `pending_asset_instances` and in the crossing's landing gate (`PendingUnder`). Review: C:/Modding/Mudcrab/mudcrab/local/agents/runs/review-1079-p2-load-pacing.1/report.md, finding 1 and the nits in §7.

- Portal Dev's notes, which you must keep:
  - If the landing cell is not resident but `destination_is_loaded` is true (everything settled, landing failed), the code warms by fiat (`warmed.extend; continue`). KEEP that branch, or a failed destination holds the tour forever.
  - `update_portal` runs before prewarm in the same chain and owns `Camera::is_active`. Prewarm only borrows it: never write `is_active` in the Load path.
  - The test `an_exterior_destination_warms_once_its_landing_cell_is_resident` (fixture `write_exterior_door_fixture`) asserts Warming on the mid-grid frame. With the new condition, its fixture's loads must have drained, or the expected phase changes. Adjust the fixture, not the meaning of the test.

# What to change
1. In the Load path of the prewarm gate: the landing cell counts as ready only when it is resident AND it has no queued and no in-flight model loads. Use the same predicate `PendingUnder` / `pending_asset_instances` uses, and keep one source of truth. With cap 0 nothing is ever queued, so the behaviour equals today's after the loads finish. Say in the report whether this changes timing at cap 0: the gate may now also wait for in-flight loads that the old one ignored. That is the intended meaning.
2. Tests (portal.rs tests):
   (a) with a cap, a landing cell that is resident but still has queued loads keeps the prewarm in Load or Warming, NOT settled, until its loads finish;
   (b) the failed-landing fiat branch still warms;
   (c) the existing landing-cell test passes with its fixture loads drained.
3. Doc (config.rs, the `max_asset_loads_in_flight` doc): one sentence saying the cap paces only the per-reference converted model loads. Terrain quadrant textures, the water flow-normal image and LOD chunk scenes are not paced; they are path-deduplicated, but the first cell of a texture set and a worldspace's first LOD chunks still finalize together.
4. Test nit (streaming.rs, test d `a_cell_despawned_with_queued_loads_never_issues_the_rest`, ~11452-11490): it asserts an exact delta on a process-global `AtomicUsize` (`PACER_LOADS_BUILT`). That is flaky under plain `cargo test`, where another test's loads run in the same process. Make the counter per-app, for example a resource or an Arc handed to the test loader.

5. **A doc claim** (from the GLM review, review-1079-p2-load-pacing.glm.1): impl-1060's comment says the prestream wait counts queued loads as not ready. Before item 1 that was false, because the wait followed the commit-time residency. After item 1 it must be literally true. Check the wording against the final code, and say exactly which gates count queued loads.
