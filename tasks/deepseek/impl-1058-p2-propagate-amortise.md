# Goal
Kill the one-frame `portal/propagate` spike (25.6-37.7 ms) that lands one frame before every door crossing, without weakening any layer contract (track: Phase 2; the 160 fps goal; brief written 2026-10-08 from upstream-dev's crossing-frames note).

# Context
- Evidence: `local/research/portal-crossing-frames-895-2666-2026-10-08.md` (read it first). `portal/propagate` spikes exactly one frame before each crossing (frame 894: 30.9 ms, 2169: 37.7, 2665: 25.6) and is back to ~2 ms on the crossing frame itself. Cause: `HierarchyPropagatePlugin<RenderLayers>` (bevy_app-0.19.0/src/propagate.rs) doing the FIRST propagation pass over the destination cell's freshly materialised entity tree (~879 nodes at the Riverwood Trader, impl-223) in one PostUpdate.
- State after impl-649 (landed): `isolate_cells` (crates/engine/src/portal.rs) no longer walks nodes; it stamps `Propagate<RenderLayers>` sources (cell roots, reference entities via `source_layers`, water/own-layer sources) and Bevy propagates down. An observer stamps a new cell root the moment `streaming::spawn_cell` inserts `StreamedCellKey` (portal.rs ~3222).
- **Why the first pass costs 37 ms (read propagate.rs and verify):** the recursion is diff-based — line ~280 skips children whose `Inherited<C>` already equals the parent value, and the repair query at ~314-319 skips the concrete write when `inherited.0 == current`. A brand-new subtree has neither `Inherited<RenderLayers>` nor the final `RenderLayers` on any node, so the first pass pays, per node: `RenderLayers` clone + two `try_insert` commands + an archetype move for each inserted component, all flushed in one frame. ~879 nodes at ~40 us/node matches the spike.
- This means a fix that pre-stamps the subtree's final values at spawn time turns the first propagate pass into a compare-only walk (near-free), WITHOUT spreading anything across frames and WITHOUT touching the one-frame rule. Candidate mechanisms, in order of preference:
  1. **Stamp at spawn (preferred):** when the cell tree is built (streaming.rs `spawn_cell` command builders, or the existing `Add<StreamedCellKey>` observer before the first PostUpdate), give every node the `Inherited<RenderLayers>` and concrete `RenderLayers` its ancestry implies. The layer values must come from the portal's logic (`role_layers`/`source_layers`), which lives in portal.rs while the tree is built in streaming.rs — keep the coupling clean (e.g. a resource/installed resolver the PortalPlugin provides, absent = no stamping when the portal plugin is off), and do NOT hardcode layers or roles into streaming.rs.
  2. **Budgeted subtree materialisation (fallback):** if measurement shows the spike is dominated by something stamping cannot remove (e.g. the entity spawn itself, not propagate), spread the destination cell's node insertion over the prestream budget frames (`portal/prestream` already exists; `transition::plan_door_prestream`) so no single frame carries the whole subtree. The cell must still be COMPLETE before the door opens — completing late is a shortcut, not an amortisation.
- Measure first: re-run or reuse a crossing capture and confirm what share of the 30-38 ms is propagate's own span vs other work on that frame. If the saved CSV already answers it (it attributes the spike to the propagate span), say so and skip the re-run.
