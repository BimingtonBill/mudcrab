# Profiling tools: which one, and how agents use them (2026-10-15)

Installed on this PC (RTX 3090): Tracy 0.14.1 (winget `wolfpld.tracy`; the engine bundles 0.14.0), PIX 2603.25, RenderDoc 1.46. Check with `python tools/perf/perf_capture.py check`. Nsight Graphics was tried and removed the same day: its command line crashed at start (exit 0xC0000409, even on notepad), and PIX covers the GPU questions here.

## Which tool for which question
| Question | Tool | Why |
|---|---|---|
| Which main-world or render-world system is slow, and where does the CPU wait? | Tracy (`perf_capture.py run tracy`), after the engine's own report (`render_timing.rs`, `schedule_timing.rs`, benchmark JSON) | per-system and per-phase CPU spans on the render thread |
| Which GPU pass costs time, on a settled scene? | the GPU table of the same Tracy capture (Bevy's own timestamp zones; `summary.md`, `gpu-zones.csv`) | per-pass GPU time next to the CPU zones, taken after the scene has loaded |
| Which GPU draw or event inside a pass costs time? | PIX (`perf_capture.py run pix`, or the PIX GUI) | per-event GPU durations (shadow cascades, depth downsample, indirect parameter building); launch-only through the wrapper |
| Is the geometry, texture or shader wrong? | RenderDoc (`--render-backends vulkan`) | per-draw state and resources |
| Did a change move frame time? | a TIMING run, only when the "worth it" rule is met (`run-classes.md`) | profilers slow the engine, so they never give the number |

## Rules
- A profiler capture is a TEST run, never TIMING. Never quote fps or frame time from one. A number you will quote comes from a TIMING run without a profiler attached.
- Start captures through `tools/perf/perf_capture.py`, which goes through `build_gate.py test` (refused, exit 4, while any hold is set; there is no queue), adds `--run-label` and `--run-owner`, writes the capture to `D:/Mudcrab/perf/<date>-<label>/` with an `OWNER.txt` and a `meta.json`, and never touches the gate. Check disk first for big jobs: `python tools/disk_guard.py --drive D: --need 2`. Traces are 10-20 MB each; delete the folder when the finding is written up.
- Capture a scene that exercises the mechanism you are asking about (the same rule as the timing "worth it" test). A `--benchmark-*` run titles its window `[TIMING]` even through the TEST gate; for a profile prefer a scene or route flag.
- Release or quick build, same flags as the run you are asking about. Debug builds tell you nothing about cost.
- Write the finding down (thread, PR text or research note): the system or pass, its cost, the capture folder. A capture nobody read is not evidence.

## Natural order for performance work (agents)
1. Name the mechanism and the prediction (run-classes.md, "Is a timing run worth it?").
2. Look at what the engine already reports (benchmark JSON phases, GPU pass timings, `render_timing`). That is free. If the render thread is the cost, take a Tracy capture of the scene (next section) and read the top zones before touching code.
3. If GPU time is unexplained: a PIX capture, read the top events.
4. If the question is "what is drawn / is this correct": RenderDoc.
5. Change the code. Only now, if the rule allows, a TIMING run for the number.

## Tracy: render-thread CPU
Most frames here are render-thread CPU bound (`research-734`, `portal-heavy-render-thread-2026-10-08`), and the engine's own report only splits that into a few phases. Tracy names every system and Bevy's render spans.
1. Build the engine with the feature: `build_gate.py run -- cargo build --profile quick -p engine --features tracy` (own target folder; `bevy/trace_tracy` makes every Bevy system a span). Never leave the feature on in a normal build: with no `tracy-capture` attached it grows memory without limit.
2. `python tools/perf/perf_capture.py run tracy --engine <that engine.exe> --owner "<thread>" --label "<scene>" -- <engine args>`. It starts `tracy-capture`, then the engine as a TEST run, then exports zone statistics (`zones.csv` inclusive, `zones-self.csv` self time) and writes `summary.md`: the top zones with total, calls, mean, max and ms per frame. Agents read `summary.md`; the `.tracy` file is for you in the viewer (`tracy-profiler`).
3. Compare two captures taken the same way (same scene, same build profile, same engine arguments): `python tools/perf/tracy_report.py diff <before>/zones.csv <after>/zones.csv`. It lists per-call mean changes, so captures of different length compare. N13 (occlusion culling on versus off) is exactly this.
4. Read inclusive time to find the phase, self time to find the system. wgpu and naga spans appear only with `RUST_LOG=info` (set it in the environment of the run to see encoder cost). If several `prepare` systems all end together, the thread is waiting for the swapchain (GPU bound): look at PIX.
5. Worked example (Riverwood one-door tour, 980 frames, quick build with Tracy, so times are inflated and only the ranking means anything):
```
python tools/perf/perf_capture.py run tracy --engine <engine.exe built with --features tracy> --owner "<thread>" --label "riverwood 1 door" -- --assets <converted> --demo riverwood --walk --demo-tour <scratch dir> --tour-doors 1
python tools/perf/tracy_report.py summary <capture>/zones.csv --match system --top 12
```
The render thread (`bevy_render::run_render_schedule`) averaged 8.3 ms per frame under Tracy, of which `render_system` (graph encode and submit) was 2.8, `submit_pending_command_buffers` 1.3, `allocate_and_free_meshes` 0.8, `camera_driver` 0.8; on the main thread `engine::streaming::lod::visibility::update_terrain_lod_visibility` cost 2.5 ms. The summary hides one-off asset-loading zones (`--keep-loading` shows them) and counts frames from `main_render_schedule`.
6. GPU passes come with the same capture. Bevy 0.19 opens a Tracy GPU context under `bevy/trace_tracy` and records a zone per render pass with timestamp queries (Vulkan and DX12; none on Metal or when the adapter has no timestamps). The wrapper exports them with `tracy-csvexport -g`, aggregates them into `gpu-zones.csv` (the zone-table layout, so `tracy_report.py summary` and `diff` work on it) and appends a "GPU passes" table to `summary.md`. Per-pass means are GPU time under the profiler, a ranking and not a frame budget; passes overlap, so the sum is not frame time. Example (the `baseline_lod_far` shot, quick build, Tracy attached): `bin_unpacking` 0.37 ms, `main_opaque_pass_3d` 0.31 ms, `bloom` 0.19 ms, `clustering` 0.12 ms per frame.
7. Tracy's overhead is in every number: it is a TEST run, never quote its times as frame time. `tracy-csvexport -u` lists every event, so the wrapper uses the aggregate form.

## Standard scenes and baselines
`perf_capture.py run tracy ... --scene <name> --assets <converted folder>` fills in the engine arguments of a named scene (`tools/perf/scenes.json`; the arguments follow `scripts/phase2-profile.ps1`, so the scene is the one the baseline report measures). Scenes: `synthetic` (no world data), `rural`, `dense` (Riverwood), `stress`, `lod-far`, `portal-heavy`, `portal-door-tour`. `--seconds` changes the window; anything after `--` is added to the engine's command line. The engine's benchmark report goes to the capture's `scratch` folder.
To compare a change: take a capture of the scene on the branch before the change, `python tools/perf/perf_capture.py baseline save <scene> <capture folder>` (keeps its `zones.csv` and `gpu-zones.csv` under `D:/Mudcrab/perf/baselines/<scene>/`), take a capture the same way after, then `baseline compare <scene> <capture folder>` lists the CPU zones and GPU passes whose mean per call changed. Same machine, build profile, engine and scene only; the baseline is overwritten by `save`, and it is a pointer for ranking changes, never a number to quote. The full fixed-scene report with spreads and a fingerprint is `scripts/phase2-baseline.ps1` (issue 184): use it when the number matters, these captures when you need to know where it went.

## Custom spans inside a system
Bevy spans every system, so a capture names the slow system but not the slow part of it. `perf_span!("area::system::phase")` (`crates/engine/src/perf_span.rs`) adds a named span for the rest of the enclosing block; without `--features tracy` it expands to nothing. Rules: a string-literal name of the form `<area>::<system or stage>::<phase>`, one per phase and never built at run time (so captures from different runs group by name), around a loop and never inside a per-entity loop. Add spans where a capture shows a system with a large self time, not ahead of it. The current `engine::streaming::lod::visibility::update_terrain_lod_visibility` phases are `lod::visibility::rebuild`, `lod::visibility::absorb` and `lod::visibility::apply`. The first rebuilds after initialization or journal recovery, the second absorbs entity-local changes, and the third selects tiers and applies affected visibility keys. Historical example, before the incremental index (`lod::visibility::collect_ready`, `select_tiers`, `apply`): in a 25 s LOD far-view capture (`lod-far`, 133 refreshes, self time from `zones-self.csv`), building the ready-patch map took 7.8 ms per refresh, the tier selection 3.4 ms and applying visibility 1.0 ms, so that historical cost was in the HashMap builds, not the visibility writes. These old phases do not map one-to-one to the current ones; compare inclusive system totals across that change. Flight attribution accepts the `lod::visibility` prefix, while `route_names.py` and `route_zones.py` accept system names generically. A span lasts to the end of its block, so a phase that must not contain the next one goes in a block of its own, and `zones.csv` (inclusive) double-counts nested spans: read `zones-self.csv` for the cost of one phase.

## Terrain index correctness audits

Add `--terrain-audit` to a played quick/release build to compare terrain identities and LOD state with full rebuilds about once per wall-clock second. Errors log `terrain audit desynchronization` with the index and reason, and cumulative checks/desyncs appear under `terrain/audit/{identity,lod}/{checks,desyncs}` in `--profile-output <dir>`'s `cpu-spans.json`. The audit logs also report event-local relationship backlink fast/linear checks, inspected siblings and exceptional recovery requests. Audit-enabled runs are correctness runs, not performance measurements. In release builds the flag defaults off; no audit clock, comparison, resource or publishing system runs when disabled. Debug assertions retain their exhaustive checks independently of this flag.

## PIX: GPU passes
`python tools/perf/perf_capture.py run pix --engine <engine.exe> --owner "<thread>" --label "<what>" -- <engine args>` captures one frame on the DX12 backend (the wrapper sets `WGPU_BACKEND=dx12`; the engine otherwise picks Vulkan, which PIX cannot capture), saves `capture.wpix`, exports `events.csv` and writes `gpu-summary.md` (top events by GPU duration; pass names from wgpu debug groups appear as `pass: <name>`). Tested on the synthetic benchmark (250k instances): shadow cascades, `late_downsample_depth` and `main_indirect_parameters_building` show as named passes.
Limits: `pixtool` captures only a process it launched, about a second after launch (`attach` to a running engine is refused), and has no "wait for N frames". So the wrapper's capture is the first frames after start: good for synthetic and early scenes. For a settled real scene open the PIX GUI (`C:/Program Files/Microsoft PIX/<version>/WinPix.exe`), launch the engine with `WGPU_BACKEND=dx12`, and press the capture button when the scene is steady. Durations are per event and overlap, so the sum is not frame time.
`pixtool` quoting: its `--command-line` takes the engine's arguments as one quoted string and cannot parse it if a shell re-quotes the token; the wrapper hands it the exact string. Calling `pixtool` by hand from PowerShell fails on arguments with spaces; use `cmd /c` with `--command-line="a b"`.
RenderDoc, scripted: build the engine with `--features renderdoc` (an optional dependency, the `renderdoc` crate, MIT or Apache 2.0; `crates/engine/src/renderdoc_trigger.rs`), then `python tools/perf/perf_capture.py run renderdoc --engine <engine.exe> --owner "<thread>" --label "<what>" --capture-frame 900 [--capture-frames 1] --scene <name> --assets <folder>`. The wrapper starts the engine under `renderdoccmd capture` on the Vulkan backend with `MUDCRAB_RENDERDOC_CAPTURE_FRAME` set; the engine asks RenderDoc for the capture itself when its main frame counter reaches that number (pick a frame after the scene has settled: the run must last at least that long, the scene window `--seconds` too) and the `.rdc` file lands in the capture folder. An engine started without RenderDoc and with the variable set stops with an error, and without the variable the hook does nothing. By hand: `renderdoccmd capture -w <engine.exe> ...` and F12.

## Known gaps
- GPU zones in Tracy: Bevy 0.19 provides them (`bevy_render::diagnostic::tracy_gpu`), so no `wgpu-profiler` is needed. They are per render pass, not per draw; use PIX for events inside a pass.
- A settled-scene PIX capture is by hand (PIX GUI); the Tracy GPU table and the scripted RenderDoc capture cover settled scenes without it.
- Custom spans exist only in `update_terrain_lod_visibility`; add more where a capture shows a large self time (see "Custom spans inside a system").
- Nsight Systems (CPU and GPU on one timeline) is the NVIDIA tool NVIDIA recommends starting with; not installed.
